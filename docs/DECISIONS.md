# Decisions

## 2026-11-01 — Kaspi first, low volume
Proceed with Kaspi public data at low volume for validation. No public consumer API exists. Revisit if Kaspi objects; consider asking for a partnership.

## 2026-11-01 — One national price
Tested 3 products across 6 cities: identical lowest price. Store one price per product; collect with Almaty's city id. Dropped `regions` from the schema.

## 2026-11-01 — Legal review (data localization) deferred to Phase 2
Use free/cheap EU-hosted services now (Supabase). Plain Postgres keeps a later move to KZ hosting cheap.

## 2026-11-01 — Stack
Next.js 15 + next-intl, Supabase Postgres via postgres.js (no ORM: SQL migrations are the source of truth), Resend, Node worker run by tsx, Vitest. Fonts self-hosted via Fontsource (Onest, JetBrains Mono) — both cover Kazakh Cyrillic and need no Google Fonts call at build time.

## 2026-11-01 — Number formatting by hand
`Intl` kk-KZ output differs between Node and browsers (hydration mismatch). `formatTenge` groups digits itself.

## 2026-11-01 — Interest capture before accounts
Until Phase 4 (magic-link auth), the coupon form stores `{email, target}` as a `feedback` row of kind `waitlist`, and says alerts are coming soon. No fake "you're tracking" confirmation.

## 2026-11-01 — Verified TLS to Postgres
postgres.js defaults to `ssl: false`, so our Supabase connections were unencrypted. All clients (web, worker, migrate) now build options with `connectionOptions()` from `@baga/db`: Supabase hosts use verified TLS against the Supabase Root 2021 CA (`packages/db/prod-ca-2021.crt`, embedded in `src/supabase-ca.ts` so it works in the Vercel bundle; expires 26 Apr 2031); other remote hosts use verified TLS against system CAs; localhost stays plain; an explicit `sslmode` in the URL wins. "Enforce SSL" is on in the Supabase project.

## 2026-11-01 — Hourly collection on GitHub Actions
The datacenter IP test passed: Kaspi answers GitHub Actions runners. The repo is private, and Actions on the free plan gives 2,000 minutes a month (each run is billed as at least 1 minute), so `collect.yml` runs hourly (`7 * * * *`) instead of every 30 minutes. That's about 1,440 minutes a month at full seed size. The shortest product interval is 60 min (`hot`), so a due product waits at most about one extra hour. If minutes run short, move collection to a small KZ VPS cron (same `pnpm worker`).

## 2026-11-01 — Collection every 4 hours (replaces "Hourly collection on GitHub Actions")
Prices change slowly, so `collect.yml` runs every 4 hours (`7 */4 * * *`, `COLLECT_EVERY_MINUTES = 240`). Actions minutes depend on total checks a day (about 2.5 s each: page + offers + polite delay), not on how often the job runs. Seed interval goes from 12 h to 20 h, so each product gets at least one check per calendar day (a test enforces seed + run spacing ≤ 24 h). Budget: 1,000 seed products ≈ 1,200 checks a day ≈ 1,600 minutes a month, inside the private-repo free 2,000. `COLLECT_BATCH=250`, job timeout 30 min, claim lock 45 min. 2,000 seeds (≈ 3,100 minutes) would need a public repo or a VPS. Hot/tracked intervals (60/180 min) currently mean "every run"; revisit in Phase 4.

## 2026-11-01 — Follow kaspi.kz/robots.txt; daily run in the visit window; public repo (replaces "Collection every 4 hours")
kaspi.kz/robots.txt asks bots for `Crawl-delay: 10` and `Visit-time: 0400-0845` (UTC = 09:00–13:45 Almaty), and lists `Sitemap: https://kaspi.kz/shop/sitemap.xml`. None of the paths we use are disallowed. We follow both directives:
- The worker's Kaspi client waits ≥ 10 s (+ up to 2 s jitter) between any two requests, including re-checks and alert confirmations.
- `collect.yml` starts once a day at 03:50 UTC; the worker waits for 04:00, claims small batches, and stops claiming at 08:45 UTC. Capacity ≈ 1,500 requests/day.
- Routine checks fetch the offers endpoint only (1 request). The product page (title, image, category) is refreshed when older than 7 days (`products.page_checked_at`).
- Seed products wait in `seed_queue`; the seed script makes no Kaspi requests. The collector fetches queued products after due ones.
- Seed interval is 18 h: longer than the 4 h 45 min window (no double check the same day), short enough that a product checked late in today's window is due before tomorrow's opens.
- Heartbeat observation is written when the last observation is on an earlier Almaty calendar day (it was "> 24 h", which left gaps with daily checks).
- Budget: ~1,300 seed products checked daily, plus products people view. Visitor-triggered lookups of unknown products (web) are single on-demand requests, outside these crawl rules, rate-limited separately (Turnstile, Phase 3).
- The repo is public, so GitHub Actions minutes are free; a ~5 h job fits the 6 h job limit. Note: GitHub disables scheduled workflows in public repos after 60 days with no commits.

## 2026-11-01 — Cloudflare Turnstile on visitor-triggered Kaspi requests
A page load never fetches Kaspi. A product page for a product we don't have shows a lookup screen (`noindex`) with an invisible Turnstile check; on success the browser POSTs `{id, token}` to `/api/lookup`, which verifies the token with Cloudflare `siteverify`, fetches the product once, stores it and the page reloads from the database. Short-link resolution in `/api/resolve` (a request to l.kaspi.kz) also requires a token. No npm dependency: the Turnstile script is loaded only where needed and verification is a `fetch`. Keys: `NEXT_PUBLIC_TURNSTILE_SITE_KEY`, `TURNSTILE_SECRET_KEY`. Without keys, development uses Cloudflare's documented always-pass test keys; production fails closed (lookups refused). Per-IP and per-instance limits stay as a second layer. Without a database (UI work), the old live-fetch path remains for development only.

## 2026-11-01 — Vercel functions in Stockholm (arn1)
The database is in Supabase eu-north-1 (Stockholm). Server code ran in Vercel's default iad1 (US East), so every query crossed the Atlantic (first product page ~3.3 s). `apps/web/vercel.json` pins functions to `arn1`, in the repo rather than only in the dashboard.

## 2026-11-01 — The website never requests Kaspi; visitor lookups are queued (replaces the on-demand fetch in "Cloudflare Turnstile on visitor-triggered Kaspi requests")
Kaspi answered the very first request from Vercel (AWS, iad1 and arn1) with 429, while GitHub Actions runners are answered normally. Rule 6 says stop on 429, so the web app no longer fetches products. After the Turnstile check, `/api/lookup` adds the product to `seed_queue` with `source = 'visitor'` (capped at 300 pending visitor rows). The daily collector, inside the robots.txt window with the 10 s delay, takes visitor rows first on every batch, then due products, then seed rows, and polls for new visitor rows every minute until the window closes, so a request made during the window is fetched within minutes. The product page shows when the price will appear (today/tomorrow, 9:00–13:45 Almaty). A product Kaspi reports as missing is kept in the queue as `not_found` so it is not requested again daily, and its page says so. Short-link resolution (`/api/resolve`, one request to l.kaspi.kz) stays on demand; if Kaspi refuses it, the visitor is asked to paste the full link. Every request to Kaspi product data now goes through the collector.

## 2026-11-01 — Nightly backup to Cloudflare R2 with an automatic restore drill
Supabase Free has no backups. `backup.yml` runs at 02:17 Almaty: `pg_dump --schema=public` over the session pooler (port 5432; `pg_dump` cannot use the transaction pooler), with a client matching the server's major version from the PostgreSQL apt repo, uploads to a private R2 bucket (free tier, 10 GB; old dumps expire by an R2 lifecycle rule), then restores the dump into a scratch Postgres of the same version and fails unless every table's row count matches. Supabase's `auth.users`/`auth.uid()` are stubbed for the drill; once Phase 4 creates user accounts, the backup must also cover `auth.users`. The derived connection string and password are masked in the public Actions logs.

## 2026-11-01 — Inline CSS (Next `experimental.inlineCss`)
Lighthouse mobile showed the 6 KB stylesheet as render-blocking (≈900 ms on a simulated slow phone). The CSS is small, so it is inlined into each HTML response; the text (the LCP element) can paint without waiting for a second request. Revert if the CSS grows past ~30 KB or the flag causes issues.

## 2026-11-01 — Seed catalog from Kaspi's sitemap, about 1,000 products
The catalog is seeded up front so search and "similar products" have something to show. Source: the sitemap kaspi.kz/robots.txt lists (`/shop/sitemap.xml`); `pnpm --filter @baga/worker discover` reads the index and a few product sitemaps (≤8 requests, ≥10 s apart, visit window only, stops on 403/429), sorts products into ~15 categories by the words of their links (accessories skipped), takes an even spread per category and writes `apps/worker/data/seed-discovered.txt` for review; the existing `seed` command queues it. No database access, no category or search APIs. Size: the window allows ~1,500 requests a day; a new product costs 2, a seed product ~1.15 a day after that, so ~1,000–1,200 products fit with room for visitors (the plan's 2,000 does not). The first fill takes about two days. The sitemap has no popularity; the per-category spread is a first cut to refine once the real files are seen.

## 2026-11-02 — Seed picking rules, from the real sitemap
The real sitemap (2 Nov 2026): index on kaspi.kz lists 350 product sitemaps (~9,000 URLs each, ~3M products, sorted by id, mixed categories, no dates or popularity) and 320 per-city category sitemaps, all on Kaspi's CDN. The first cut (category word only, even spread over 7 files) let in cases (`dlja` = "for"), fabric softener (`konditsioner`) and unknown brands. Now a product needs a category word **and** a well-known brand for that category, accessories and spare parts are excluded (including Kaspi's soft-sign hyphen, `fil-tr`), newest ids come first (current models), and one colour per model is kept. `discover` reads the index + 40 product sitemaps (≈8 min at 10 s spacing; only the index is on kaspi.kz).

## 2026-11-02 — Short links the website cannot resolve are queued for the collector
Kaspi does not answer Vercel on l.kaspi.kz either: the resolver hung until Vercel's 300 s limit ("Task timed out"). The website now tries for at most 4 s (the request also has a timeout now) and otherwise stores the link's validated path in `short_link_queue` (migration 0006) and sends the visitor to `/l/<code>`. Inside the visit window the collector resolves queued links first (one non-following GET of `https://l.kaspi.kz` + path, same spacing and circuit breaker), queues the product as a visitor request and fetches it right away; `/l/<code>` refreshes and forwards to the product page. No proxies or other networks: Kaspi's choice not to answer Vercel is respected.

## 2026-11-02 — Tracking before registration, alerts in Telegram
Visitors should never get only "come back tomorrow". Kaspi's robots.txt still rules out a live price outside 09:00–13:45 Almaty and from Vercel, so the answer is to start tracking at once and deliver the price when it arrives: the coupon on every product page (also on a queued product's page) saves the visitor's own price immediately, and the collector sends the first observed price, then target alerts, to Telegram within a minute of each check.
- **No account yet.** A visitor is an anonymous *watcher* (migration 0007): a random 256-bit secret in an httpOnly cookie, and in a private link (`/api/my?k=…`) to open the list on another device. Only its SHA-256 is stored. "Мои товары" (`/my`) lists, and lets them remove, what they track. Phase 4 moves a watcher's trackings into a registered account and adds plan limits (5 free, more paid); until then a 20-per-watcher cap stops abuse.
- **Telegram before email**, because email needs a domain of our own (Resend will not send to strangers from `vercel.app`); Telegram needs only a bot. A one-time deep link `t.me/<bot>?start=<code>` connects the chat (`/list`, `/stop` in the bot). The webhook (`/api/telegram/webhook`) only accepts Telegram's secret header. No dependency: the Bot API is plain `fetch`.
- A watcher tracking may point at a product that is only queued (`trackings.external_id`; `product_id` is filled in when the collector first saves it). Trackings can only be made for products in the catalog or queue. Products with trackings move to the 3 h "tracked" priority, within the same daily request budget.
- Considered from the author's earlier project: reading Kaspi's Open Graph `product:price` tags. It is still a Kaspi request, so it cannot give a price outside the window or from Vercel; kept in mind as a fallback parser once a full product page is captured as a fixture.

## 2026-11-02 — Unreadable responses do not stop the collector; one odd seller entry does not lose a product
The 2 Nov run stopped after 14 checks because 3 offers responses failed schema validation (21% > 20%). Kaspi was answering normally; our parser was too strict. Now: offers are validated one by one and only the seller id and a positive price are required (a seller without a name is shown by id; entries without a price are skipped, never guessed). The circuit breaker still stops at once on 2 responses with 403/429 and on > 20% other failures, but parse errors count separately and stop the run only above 50% over ≥ 20 checks, which means Kaspi changed its format. Parse errors now log the failing fields.

## 2026-11-02 — Email alerts with confirmation (bagaapp.com)
Not everyone uses Telegram. Email needs a domain of our own: **bagaapp.com** (Namecheap), verified in Resend (DKIM, SPF via the `send` subdomain, DMARC `p=none`). A watcher can connect Telegram, email, or both; every alert goes to each connected channel (one `notifications` row per channel; email keys end in `:email`).
- **Double opt-in.** The coupon and "Мои товары" take an address after Turnstile; the website sends a confirmation link (the only email it sends) and alerts start once the owner presses "Подтвердить" on `/[locale]/email?confirm=…`. Only the SHA-256 of the token is stored; it expires after 2 days. Confirming and unsubscribing need a button press (POST), so mail scanners that open links change nothing.
- **Abuse limits:** 5 requests an hour per IP, one a minute per watcher, 5 a day per address across all watchers.
- **Unsubscribe:** every alert has a visible "Не присылать письма" link and the RFC 8058 one-click header (`/api/email/stop?c=…`), which Gmail and Yahoo expect. Unsubscribing forgets the address.
- Migration 0008 adds the columns to `watchers`. The old email path for registered users (`auth.users`, `profiles`) is gone from the collector: no accounts exist yet, and Phase 4 moves watchers into accounts.
- No new dependency: Resend is a plain `fetch`. Personal data: an email address is now stored, which makes the privacy policy (Phase 5) a launch blocker.

## 2026-11-02 — Tracking a short link before it is resolved
Links shared from the Kaspi app are `l.kaspi.kz` short links, and Kaspi usually does not answer Vercel, so the visitor lands on `/l/<code>` without a product id. That page now has the same price form: the tracking is stored on the short link (`trackings.short_link_code`, migration 0009). When the collector resolves the link in the visit window, it moves the waiting trackings onto the product (a watcher who already tracks that product keeps the existing one), and the first price follows the product's first check. "Мои товары" and the bot's `/list` show such an item as "Товар по ссылке из приложения Kaspi" linking to `/l/<code>`.


## 2026-11-02 — Real numbers on the home page
The "Что в чеке" slips used invented numbers (labelled as a sample). They are replaced by a **Z-report**: the cash register's end-of-shift totals, stamped with the real start and end time of the latest collector run. Every number is counted from what the collector stored (`getPlatformStats`): active products, Kaspi sellers seen, checks (`collection_runs.checked`), price changes and drops (a drop needs two consecutive observations of a product, so a first price never counts), checks per Almaty day. Under it, receipt slips list real products linking to their pages: the biggest drops and rises (switchable: the latest day with any change, or the last 7 days; one line per product), the biggest drop of the week, the most tracked products (ordered by number of trackings; the counts are not shown) and the newest products in the catalog.
- Small numbers stay hidden until they mean something: people tracking prices from 100 (watchers are browser cookies, so this is a ceiling, not a head count), alerts sent from 50. The section is not shown at all before the first finished run or without a database; no sample numbers take its place.
- Read by the browser from `/api/stats`, which the CDN caches for an hour (the numbers change once a day). The home page stays static and its build never needs the database. No new table or dependency; if the window queries over `price_observations` get slow, the collector can write a daily summary row instead.
- The hero receipt stays a stamped ОБРАЗЕЦ until real products have about a month of history.

## 2026-11-02 — Safety margins inside Kaspi's visit window
Kaspi's robots.txt window is 04:00–08:45 UTC. The collector now sends requests only 04:05–08:30 UTC (09:05–13:30 Almaty): 5 minutes after it opens and 15 before it closes, so runner clock drift, a slow last request or retries never touch the edges. One constant, `COLLECT_WINDOW_UTC` in `packages/core/src/window.ts`, drives the worker, `discover`, `probe` and the website's "today/tomorrow" and "fetching now" texts. Capacity drops by about 7% (≈ 1,400 requests a day). The cron triggers stay; GitHub sometimes delivers them hours late (2 Nov: two triggers arrived at 11:42 and 13:52 UTC), and such a run finds the window closed, sends queued Telegram and email messages and exits within seconds without any Kaspi request.

## 2026-11-03 — Percentage targets for products without a price
The coupon offers one-tap ranges: 5–10%, 10–25%, 25% or more cheaper. A range alerts at its smaller percentage, as a round price (`targetForDrop` in core). A product still waiting for its first price has nothing to take a percentage of, so its tracking stores the percentage instead (migration 0010: `trackings.target_drop_pct`, `target_price` may be null while it is set). The collector turns it into `target_price` when it saves the first price, before the first-price message, so that message already says "Ваша цена: …" in tenge. Alert evaluation skips trackings without a price. If the price arrives between the page load and the tap, `/api/track` converts the percentage itself. Own-number targets stay as they were.

## 2026-11-03 — Variant links (clothes, shoes) resolved by the collector; visitor products retried
About 6.5% of Kaspi product links (12,965 of 200,000 sampled from the sitemaps on 3 Nov) end in a group code, 8 digits and a letter (`…-15956323b/`), instead of a product id. They name a product with variants (sizes, colours); `https://kaspi.kz/shop/p/-<code>/` answers 302 to one concrete product (`…-134007098/?hasVariants=true`), confirmed for three codes. The website still never requests kaspi.kz: a pasted variant link, after Turnstile, goes to `short_link_queue` with path `/shop/p/-<code>/`, and the collector resolves it with one non-following GET inside the window, like a short link. A short link that points to a variant link takes one more such GET. The resolved product is the variant Kaspi picks, not necessarily the size the visitor looked at; prices of sizes rarely differ, and the product page names what we track.
Visitor products whose three attempts failed (for example on a parser bug fixed later) get their attempts reset at the start of each run for 14 days, so a fix reaches them without manual work.

## 2026-11-03 — A channel is required to finish tracking
A tracking without Telegram or a confirmed email can never alert anyone, which is the point of the app. After the tap, the coupon shows a framed "last step" box (Telegram button, or email) until one channel works; the page re-checks `/api/my/channels` on focus and every 4 s for 5 minutes after the Telegram button is tapped, so the box turns into "✓ Telegram" without a reload. "Мои товары" shows the same warning while no channel is connected.

## 2026-11-03 — Admin page
`/ru/admin` (and `/kk/admin`) is a read-only health page for the owner: collector runs with checks counted from observations (live/cancelled/aborted), queues, errors, notifications by channel and status, visitors by channel, trackings and catalog numbers, plus warnings (window open but no checks for 20 minutes, unsent notifications, trackings without a channel). It exists only when `ADMIN_TOKEN` (24+ characters) is set in Vercel; the token is POSTed once (rate-limited) and the browser keeps an httpOnly SHA-256 of it for 30 days. noindex. No new dependency. It has no visit counts: the site has no analytics.

## 2026-11-03 — External trigger for the collector (cron-job.org → workflow_dispatch)
GitHub's scheduled triggers for this repository arrive hours late or never (collector: 2 Nov at 11:42, 13:52 and 17:04 UTC, nothing on 3 Nov; the 21:17 backup arrived at 02:55). The collector's start now comes from cron-job.org (free), which POSTs to `/repos/abzalyessengazy/baga/actions/workflows/collect.yml/dispatches` with `{"ref":"main"}` at 03:50 UTC, plus backups at 04:20, 05:20, 06:20 and 07:20 UTC. The token is a fine-grained GitHub token limited to this repository with only "Actions: read and write"; it can start workflows, not read secrets or change code. It expires after a year (renew it then). The GitHub `schedule:` lines stay as a further backup. The workflow's `concurrency` group keeps one collector at a time, and a trigger outside the window exits without any Kaspi request, so extra triggers are harmless.
